# 04 · A worker cannot join the cluster

> Uses the [kubeadm cluster](../kubeadm/README.md) and the prepared machine `k8s-lab` from [03](03-kubeadm-init-failure.md).
> Time: 15 minutes.

## Problem

`k8s-lab` should become a second worker. Someone sends you a join command from their notes. It looks right. Run it (on
your computer; Multipass carries the command to the machine). We give it 90 seconds: a failing join does not give up on
its own for several minutes.

```bash
OLD=$(echo "$JOIN" | sed -E 's/--token [a-z0-9]{6}\.[a-z0-9]{16}/--token abcdef.0123456789abcdef/')
```

## Symptoms

The join hangs in the **discovery** phase: the worker keeps retrying to get the cluster's information and never gets to
the point of starting its kubelet. On the control plane, no new node appears:

<!-- test: on=k8s-cp; absent=k8s-lab; output -->
```bash
kubectl get nodes
```

```text
NAME         STATUS   ROLES           AGE     VERSION
k8s-cp       Ready    control-plane   5m13s   v1.37.1
k8s-worker   Ready    worker          4m37s   v1.37.1
```

## Initial investigation

A join needs three things to be right. Check them in this order, from the bottom up:

1. **Network:** can the worker reach the API server on TCP 6443? (firewalls, security groups, wrong IP)
2. **API server:** does it answer?
3. **Credentials:** is the token valid, and does the CA hash match?

## Output interpretation

The API server is reachable and healthy, but the token `abcdef.0123456789abcdef` is not in the list. The join's own
log (with `--v=2`) said the same thing from the worker's side: `could not find a JWS signature in the cluster-info
ConfigMap for token ID "abcdef"`. Every valid token signs the public `cluster-info` ConfigMap; no signature for
this token ID means the cluster does not know the token. Bootstrap tokens
expire (after 24 hours by default) and are deleted; a join command copied from old notes, a wiki or a chat message is
very likely stale.

## Root cause

An expired (or simply wrong) bootstrap token. The worker cannot authenticate to download the cluster information, so it
retries until it times out.

### The other classic cause: a firewall

The same hanging join happens when TCP 6443 is blocked between the machines. Here is what that looks like, so you
recognise it. Block it on purpose on `k8s-lab`, test, and remove the rule again:

<!-- test: fail; contains=refused; output -->
```bash
CP_IP=$(multipass info k8s-cp | awk '/IPv4/ {print $2; exit}')
multipass exec k8s-lab -- sudo iptables -I OUTPUT -p tcp --dport 6443 -j REJECT
multipass exec k8s-lab -- nc -zv -w 3 "$CP_IP" 6443
```

```text
nc: connect to 10.97.7.168 port 6443 (tcp) failed: Connection refused
```

<!-- test: contains=succeeded -->
```bash
CP_IP=$(multipass info k8s-cp | awk '/IPv4/ {print $2; exit}')
multipass exec k8s-lab -- sudo iptables -D OUTPUT -p tcp --dport 6443 -j REJECT
multipass exec k8s-lab -- nc -zv -w 3 "$CP_IP" 6443
```

In a cloud, the equivalent is a security group or network ACL that does not allow 6443 from the workers. `nc -zv` (or
`curl -k https://<ip>:6443/version`) tells the two cases apart in seconds.

## Fix

Always generate a fresh join command on the control plane, right before you use it:

<!-- test: timeout=600; contains=This node has joined the cluster; output=tail:6 -->
```bash
JOIN=$(multipass exec k8s-cp -- sudo kubeadm token create --print-join-command)
multipass exec k8s-lab -- sudo $JOIN
```

```text
...

This node has joined the cluster:
* Certificate signing request was sent to apiserver and a response was received.
* The Kubelet was informed of the new secure connection details.

Run 'kubectl get nodes' on the control-plane to see this node join the cluster.
```


## Lesson learned

- Debug a join from the bottom up: network (`nc -zv`), API server (`/version`), then credentials (`kubeadm token list`).
- Never reuse an old join command: `kubeadm token create --print-join-command` takes a second.
- The CA hash protects the worker: it refuses a control plane whose certificate does not match.
- Remove nodes properly: `drain`, `delete node`, then `kubeadm reset` on the node.
